# 식사 기록·평가·체험 자료 가져오기

계획한 음식/양과 실제 먹은 음식/양을 구분한다. 계획에서 기록하면 계획은 보존하고 실제 식사 기록을 별도로 저장한다. 직접 입력 음식은 분량 모름을 허용하며, 알 수 없는 영양은 0이나 추정값으로 채우지 않는다.

## API

| 요청 | 동작 |
| --- | --- |
| `POST /api/meals` | 등록 음식 또는 직접 입력 음식 기록 |
| `GET /api/meals` | 본인 기록, 기본 활성 기록·선택 취소 기록, 항목 단위 페이지 |
| `GET /api/meals/{meal_id}` | 본인 기록 상세 |
| `PATCH /api/meals/{meal_id}` | 실제 분량·시간·메모 수정 |
| `POST /api/meals/{meal_id}/cancel` | 기록 취소. 계획과 연결된 한 끼는 묶음 취소 |
| `POST /api/meals/{meal_id}/restore` | 취소 기록 복원. 이후 계획이 바뀌었으면 거절 |
| `GET /api/meals/{meal_id}/changes` | 수정·취소·복원 전 자료 |
| `GET /api/meal-groups` | 한 끼를 나누지 않는 묶음 단위 페이지 |
| `POST /api/plans/{plan_id}/meals/{meal_key}/record` | 계획 음식의 실제 양과 안 먹은 음식 확인 후 기록 |
| `GET /api/plans/{plan_id}/actual-meals` | 현재 연결된 활성 기록으로 실제 섭취 요약 |
| `GET /api/feedback` | 본인 평가 목록 |
| `PUT /api/feedback` | 평가 저장/변경 |
| `DELETE /api/feedback/{feedback_id}` | 본인 평가 삭제 |
| `GET /api/guest-data` | 로그인 후 현재 브라우저 체험 자료 개수 확인 |
| `POST /api/guest-data/import` | 명시적으로 체험 자료를 현재 계정으로 가져오기 |

## 양·영양·계획의 구분

등록 음식은 `food_id`, `portion.amount`, `portion.unit`를 보낸다. 서버가 공식 기준으로 계산하며 당시 출처·단위·영양을 저장한다. 직접 입력은 `name`을 보내고 `portion`은 생략할 수 있다. `food_id`와 `name`을 동시에 보내지 않는다. 식사 시각에는 시간대가 필요하고 서버 시각보다 5분 넘게 미래이면 거절한다.

계획 기록은 `expected_version`, `client_record_id`, `eaten_at`을 보낸다. `amounts`에 구성 음식의 `item_id`별 실제 g을 넣고, 생략하면 해당 계획 분량을 사용한다. `skipped_item_ids`에는 안 먹은 음식을 넣는다. 같은 음식을 먹은 양과 안 먹음에 동시에 넣거나 전부 안 먹음으로 저장하지 않는다. 직접 입력은 실제 양을 null로 둘 수 있다. 등록 메뉴는 양이 필요하다. 끼니별 실제 기록의 이름·양·영양은 계획과 별도로 조회한다.

기록 후 계획은 먹은 상태로 고정되어 자동 변경을 막는다. 실제 기록만 수정하면 계획 메뉴/분량은 바뀌지 않는다. 등록 기록의 분량 재수정은 최초 저장한 단위 기준을 유지해 반올림을 반복 누적하지 않는다. g와 mL를 임의 변환하지 않는다. 연결 기록이 누락·취소됐거나 소유자가 다르면 실제 요약은 unavailable이며 계획 수치로 대체하지 않는다. 읽기 과정에서 옛 기록을 다시 쓰지 않는다.

기록 수정·취소·복원은 현재 `expected_version`을 요구한다. 같은 요청 번호·본문의 재시도는 원결과를 돌려주며 오래된 버전이나 다른 본문은 409다. 다른 소유자의 기록은 조회·수정·평가할 수 없다. 취소는 삭제가 아니며 원기록과 변경 이력은 보존한다.

## 평가와 취향 반영

식사 평가는 `phase=consumed`, `context_id=meal_id`, 해당 기록의 `food_id`(직접 입력이면 null), `rating=like|neutral|dislike`, 선택 `reason=taste|portion|unavailable|purpose|variety`를 보낸다. 같은 맥락·음식의 재저장은 기존 평가를 갱신한다. 직접 입력 음식도 평가할 수 있지만 임의로 공식 음식과 매칭하지 않는다.

명시적인 `taste`만 다음 추천의 취향 점수에 반영한다. 이유 없음·양·오늘 먹기 어려움·목표·다양성은 평가 기록으로 남기고 메뉴 취향으로 누적하지 않는다. 실제 식사의 taste 가중치는 ±0.06이며 중립은 0이다. 취소된 식사 평가는 취향 계산에서 빠지고 복원하면 다시 유효해진다. 같은 음식/단계는 최근 명시적 taste를 사용하며 합계는 ±0.09로 제한한다. 제외·준비 조건을 취향으로 우회하지 않는다.

`phase=recommendation`은 소유권과 후보가 확인되는 기존 추천 발급 자료를 참조하는 계약이다. 이번 식단 서버는 별도 `/api/recommendations` 발급 API를 연결하지 않는다. 하루 계획 ID를 이 평가의 context_id로 대신 넣지 않는다. 현재 핵심 흐름에서는 실제 식사에 대한 평가를 사용한다.

## 체험 자료 이관

가입·로그인은 체험 계획/기록/평가/설정을 자동으로 옮기지 않는다. 로그인 후 같은 브라우저에서 `GET /api/guest-data`로 확인하고, 사용자의 명시적 선택으로 `POST /api/guest-data/import`에 새 `client_request_id`와 `include_settings`를 보낸다. 브라우저 쿠키를 잃었거나 다른 브라우저에 있던 자료는 찾을 수 없다.

계획·식사 기록·평가·변경 이력의 식별자와 연결을 유지하며 소유권을 계정으로 옮긴다. 계정 설정이 이미 있으면 보존하고, 없을 때만 include_settings=true에 따라 복사한다. false면 설정을 복사하지 않는다. 원 체험 설정은 이관 완료 표식과 함께 보존하되 새 체험 쿠키에서는 노출하지 않는다.

서버는 체험 자료와 대상 계정의 이관 요청을 잠금으로 직렬화한다. 요청 번호 충돌은 양쪽 자료를 변경하지 않고 409로 중단한다. 중간 DB 실패는 전체 롤백하며 같은 요청 번호로 재시도할 수 있다. 완료 재시도는 이전 결과를 반환한다. 완료된 체험 쿠키는 교체하고 옛 쿠키의 쓰기는 차단하며 읽기 때 새 체험으로 전환한다. 다른 계정이 이미 가져온 자료를 다시 가져올 수 없다.

현재는 체험 자료 이관 API까지 연결돼 있다. ‘나중에’의 보류 상태 기억과 내 설정의 다시 가져오기 화면은 아직 연결하지 않았다.
